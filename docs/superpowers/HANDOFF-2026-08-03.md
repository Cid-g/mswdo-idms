## 1. What this system is

**Secure Municipal ID Issuance and QR-Based Verification System Using Hyperledger Fabric** —
an undergraduate thesis for the MSWDO of Gerona, Tarlac, Philippines. It issues government
IDs to three citizen categories: PWD, Solo Parent, Senior Citizen.

Stack: Node/Express + MongoDB + React/Vite + Hyperledger Fabric 2.5 (WSL2, single machine).

Start with [MASTER_PLAN.md](../MASTER_PLAN.md) for the domain model and workflows.

## 2. The deployment problem being solved

The system runs **entirely locally** in the municipal office. Applicant records never leave
that machine. But every printed ID carries a **QR code**, and the people scanning it are
outside the office: pharmacies, groceries, transport operators granting legally mandated
discounts.

Today `VERIFICATION_BASE_URL=http://localhost:5173/verify`. A phone outside the office LAN
cannot resolve `localhost`, so public verification does not work at all in the real
deployment scenario.

### 2.1 Constraints — all five hold simultaneously

| # | Constraint | Source |
|---|---|---|
| 1 | Applicant PII stays local — names, addresses, birthdates, photos, signatures | Client requirement |
| 2 | Verification works **24/7**, including when the office PC is off | User decision, 2026-08-02 |
| 3 | Revocation must be **immediately visible** externally | User decision, 2026-08-03 |
| 4 | Verifiers are ordinary establishments — **no app install** | User decision, 2026-08-03 |
| 5 | **No inbound** network connection to the office | User decision, 2026-08-03 |

**Do not relax any of these without asking the user.** Each one eliminates a whole class of
solution:

- (4) kills signed-QR schemes needing a verifier app, and kills LAN-only verification.
- (3) kills purely offline self-verifying QR — a printed card cannot know it was cancelled.
- (2) kills a tunnel to the office PC.
- (5) kills live Fabric ledger queries from the cloud.
- (1) kills replicating applicant data.

Together they admit exactly one shape: **an outbound-synchronized, PII-free cloud replica.**

### 2.2 The clarification that resolved a false alarm

The user initially said *"walang masave sa cloud"* (nothing saved to the cloud), which reads
as prohibiting any cloud storage. On 2026-08-03 they clarified:

> *"walang information pero may magsysync yung halimbawa yung token na naka encrypt basta wag
> lang yung exact data basta yung restricted na necessary para mavalidate ng external"*

Meaning: **no exact/personal data.** An opaque token plus the minimum needed for external
validation is explicitly wanted. The architecture was correct; the phrasing was stricter than
the intent.

**Open item:** the user does not know *why* the client asked for this. If the concern is
privacy, the current design satisfies it. If the concern is *"no private company should hold
any government record"*, that is about **control**, not privacy, and removing PII does not
address it. The user was asked to check. **If they come back saying it is about control, the
architecture needs rethinking — escalate rather than proceeding.**

## 4. Already done — Phase 0 (2026-08-03)

Four defects were found by an adversarial review and fixed. **Do not undo these.**

### 4.1 Fabric ledger was destroyed on every stop/start ⚠️ was the worst one

`fabric-stop.sh` and `fabric-start.sh` both called `network.sh down`, which removes
containers **and volumes and crypto material and the ledger**. Every routine stop wiped all
anchored records, while `txId`/`blockNumber` in MongoDB survived and pointed at transactions
that no longer existed.

Now three scripts with distinct roles:

| Script | Behaviour |
|---|---|
| [fabric-stop.sh](../../scripts/fabric-stop.sh) | `docker stop` — **ledger preserved** |
| [fabric-start.sh](../../scripts/fabric-start.sh) | Detects existing containers → resumes; otherwise creates fresh (and warns the ledger is empty) |
| [fabric-reset.sh](../../scripts/fabric-reset.sh) | **New.** Deliberate destruction, behind a `type 'destroy'` prompt |

Exactly one real `network.sh down` remains in the repo, inside `fabric-reset.sh`.

> **Not yet verified by a human.** The user was asked to run stop → start → verify a
> previously anchored ID. If they report a Fabric connection error after resume, check
> `FABRIC_PRIVATE_KEY_PATH` — the original script's comments say the key path changes on every
> restart. On the resume path it should not change (crypto is preserved), but this is untested.

### 4.2 `revokedReason` was public

[verifyController.js](../../backend/src/controllers/verifyController.js) returned it and
[VerificationPage.jsx](../../frontend/src/pages/VerificationPage.jsx) rendered it, on a
public unauthenticated endpoint. It is staff-written free text that may contain medical
details, alleged offences, addresses, or third-party names.

Removed from both. Still visible to staff in authenticated views.

Protected by a regression test in
[verify.test.js](../../backend/tests/integration/verify.test.js) — *"reports REVOKED status
without leaking the revocation reason"*. The test was confirmed to **fail** when the bug is
reintroduced, so it is real protection rather than decoration.

> Note: `revokedReason` is also written immutably into Fabric by
> [id-contract.js](../../blockchain/chaincode/id-contract.js). That is **not fixed** and
> cannot be un-written. See §6.2.

### 4.3 Anchors were recorded for failed transactions

[blockchain.js](../../backend/src/services/blockchain.js) called `getStatus()` but never
checked `status.successful`, so a `BlockchainAnchor` row could be written for a transaction
that never committed. Now throws if the commit failed.

### 4.4 Test baseline

**142 tests, 14 suites, all passing** as of this handoff. Run `npx jest` in `backend/`.
Jest reports an open-handles / forced-exit warning — pre-existing, not investigated.

## 6. Corrections the review forced

### 6.1 "Zero PII in the cloud" is false — must be reworded

Phase 2 claims this. It is wrong, and a panel could puncture it.

- `idType: PWD` reveals disability — **sensitive personal information** under RA 10173, a
  stricter category than ordinary PII. `SENIOR_CITIZEN` implies age; `SOLO_PARENT` implies
  family circumstances.
- `idNumber` is government-issued information peculiar to a person.
- `maskedName` retains initials, word count, and word lengths.
- Exact dates are joinable with municipal distribution rosters.

The defensible description is:

> **a data-minimized, pseudonymous verification record that still processes personal and
> sensitive personal information**

Keep the design — the minimization is genuine and worth doing. Fix the **claim**.

Note in the design's favour: hashing the UUIDv4 token is *not* security theatre. It
materially protects against a database-only dump.

### 6.2 `revokedReason` on-chain is unfixable and needs a decision

Removing it from the public API (§4.2) does not remove it from Fabric, where
[id-contract.js](../../blockchain/chaincode/id-contract.js) writes it permanently. Free-text
possibly-medical data in an immutable ledger is a genuine problem — it conflicts with any
erasure obligation.

Options: stop passing the reason to the chaincode and store only a coded enum
(`FRAUD`, `DECEASED`, `DUPLICATE`, `OTHER`), keeping free text local-only. **Ask the user
before changing chaincode** — it affects existing anchors.

### 6.3 Fabric's trust claim needs scoping, not deletion

The reviewer argued Fabric is "decorative" here. The technical core of that is right: the repo
uses two logical orgs, but both — plus keys, peers, orderer, and storage — live on one laptop
under one operator. That is **one trust domain**. Fabric provides no independent consensus
against the party running the system.

The wrong response is deleting Fabric. The right one is scoping the claim honestly:

> The prototype demonstrates the anchoring mechanism and tamper-evidence within a single
> administrative domain. Production deployment requires persistent peers operated by
> genuinely independent entities — MSWDO, municipal IT, and a third authorized agency — with
> explicit endorsement policies and backup governance.

That is defensible before a panel. *"This is immutable"* while one laptop runs everything is
not.

Related, and genuinely unaddressed: **the anchored hash does not cover the QR token or the
lifecycle status.** See [blockchain.js `buildCanonicalSnapshot`](../../backend/src/services/blockchain.js).
The receipt proves issuance, not current validity. Phase 2's public "blockchain-anchored" badge
should not be read as proof of current status. Either bind token + state version into a
verifiable object, or narrow the wording.

## 7. Traps in Phase 1 — read before writing the outbox

The reviewer identified specific ways a naive outbox still loses data. The spec covers some;
these are the ones to be careful about.

1. **"Same request flow" is not atomicity.** If Mongo commits and the process dies before the
   outbox insert, the intent is gone. Use a transaction or a same-document pending marker.

2. **Expiry has no rediscovery path.** If the expiry job commits `EXPIRED` locally but the
   enqueue fails, the next run scans only `ACTIVE` and never sees it again.

3. **Revision vs. backup restore.** Cloud at revision 5; local restored from a backup at
   revision 3; a genuine revocation becomes revision 4; the cloud rejects it as stale and the
   worker marks it sent. **The ID stays ACTIVE publicly.** Needs restore epochs or full
   resynchronization.

4. **Error-string matching is a weak correctness boundary.** The spec's idempotency relies on
   matching chaincode error text. "Already exists" does not prove the existing record has the
   *expected* hash, and wrapped or reworded errors produce false negatives. Prefer operation
   IDs in the chaincode plus state reconciliation after ambiguous outcomes.

5. **Predecessor blocking must cover FAILED, not just PENDING.** If ANCHOR reaches `FAILED`,
   a REVOKE sees no pending predecessor, runs against a nonexistent chain record, and also
   fails.

6. **Revocations should not give up.** The spec's 20-attempt cap then `FAILED` is wrong for
   revocation specifically — retry indefinitely with alerting. A permanently abandoned
   revocation is the exact failure this work exists to prevent.

7. **Worker leases are missing from the spec.** Add atomic claim, `PROCESSING` state, owner,
   and stale-lease recovery, or two workers will double-submit.

Also worth fixing while in this code: the Fabric connection is attempted once at startup with
no reconnect ([server.js](../../backend/src/server.js)), and the chaincode uses `new Date()`
inside endorsed transactions, which is nondeterministic across peers — it should use the
transaction timestamp.

## 8. Known issues deliberately deferred

- **`backend/.env` is committed to git** (commit `d20ad3a`, pushed to `origin/main`) and
  contains `JWT_SECRET` and seed passwords. There is no `.gitignore` entry for it.

  Verified: the repo is **private**, has **one collaborator** (the owner), and **zero forks**.
  So this is not currently a breach, and the user chose to defer it.

  **It must be fixed before any collaborator is added or the repo is made public.** Minimum:
  untrack, add to `.gitignore`, rotate `JWT_SECRET`. Raise this proactively if the user
  mentions adding an adviser or groupmate.

  Consequence for Phase 2: the spec says the Ed25519 private key goes in `backend/.env` and
  "never in git". That is currently false. Fix the tracking before generating the key.

- **QR generation falls back to `localhost`** silently
  ([idGeneration.js](../../backend/src/services/idGeneration.js)). Production should fail
  closed without an approved HTTPS origin.

- **Verification responses lack `Cache-Control: no-store`**, so a stale VALID could outlive a
  revocation in a cache.

- **`MONGODB_URI` is logged in full** at startup ([server.js](../../backend/src/server.js)).

- All current records are **sample data**, to be wiped before real deployment. No migration
  or backfill is needed for anything.
